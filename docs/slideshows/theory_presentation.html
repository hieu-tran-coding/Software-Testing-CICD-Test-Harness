Nền Tảng Tự Động Hóa

Ba Mức Độ Tự Động Hóa Trong Phát Triển

Continuous Integration (CI)

  • Tích hợp thay đổi vào nhánh dùng chung thường xuyên.
  • Tự động Build và Test (Lint, Unit, API) ngay lập tức.
  • Phát hiện sớm lỗi biên dịch và conflict.
  • Đề tài áp dụng: GitHub Actions chặn mã lỗi gộp vào nhánh chính bằng Quality Gates.

Continuous Delivery (CD)

  • Duy trì phần mềm ở trạng thái luôn sẵn sàng phát hành.
  • Tự động đóng gói Artifact (Docker Image).
  • Cần phê duyệt thủ công mới lên production.
  • Đề tài áp dụng: GHCR lưu trữ image đã qua kiểm chứng, bàn giao cho Jenkins.

Continuous Deployment

  • Tự động hóa hoàn toàn đến tận môi trường Production.
  • Không cần phê duyệt thủ công.
  • Yêu cầu bộ test cực kỳ đáng tin cậy.
  • Đề tài chỉ tập trung ở mức CI và Continuous Delivery.

Phân Tích Lý Thuyết CI/CD

Pipeline, Quality Gates & Nguyên Tắc Fail-Fast

Khái niệm Pipeline

Pipeline là sự mô hình hóa quy trình phân phối phần mềm thành các bước có thứ tự hoặc quan hệ phụ thuộc lẫn nhau. Nó chuyển đổi mã nguồn thô thành một sản phẩm có thể triển khai thông qua các giai đoạn: Chuẩn bị → Kiểm tra → Đóng gói.

Quality Gate (Cổng Chất Lượng)

Là điều kiện bắt buộc phải đạt trước khi artifact (sản phẩm đầu ra) được chuyển sang giai đoạn sau. Nếu Unit Test hoặc Security Scan thất bại, Quality Gate sẽ đóng lại, ngăn chặn các đoạn mã lỗi được merge hoặc deploy.

Nguyên tắc Fail-Fast trong thiết kế

Cho phép dừng sớm toàn bộ Pipeline ngay khi một điều kiện bắt buộc thất bại (ví dụ: lỗi cú pháp Lint). Điều này giúp tiết kiệm tài nguyên máy chủ CI, đưa ra phản hồi tức thì cho Developer để sửa lỗi (Fix-forward) thay vì phải đợi hàng chục phút để biết kết quả cuối cùng.

Phân Tích Lý Thuyết CI/CD

Tính Kháng Lỗi (Resilience): Kịch Bản Xử Lý Sự Cố

Pipeline không chỉ để tự động hóa lúc suôn sẻ (Happy Path), mà quan trọng hơn là cơ chế bảo vệ hệ thống khi xảy ra lỗi.

Trường Hợp Sự Cố Phát Hiện & Tác Động Chiến Lược Xử Lý Đề Xuất
1. Lỗi Code ở pha CI
(Compile error, Test fail)		 Phát hiện sớm ở bước 1-6. Pipeline bị chặn ngay lập tức (Fail-Fast). Ngăn chặn lệnh Merge. Gửi cảnh báo. Developer sửa mã nguồn trên nhánh phụ và push lại.
2. Lỗi sau khi Merge
(Lọt qua CI)		 Phát hiện ở Staging hoặc do review muộn sau khi mã đã vào nhánh main. Sử dụng lệnh git revert để tạo commit đảo ngược. Tuyệt đối không dùng git reset để tránh phá hỏng lịch sử Git chung.
3. Sự cố trên Production
(Lỗi runtime, hiệu năng)		 Phát hiện qua hệ thống Monitoring (bước 11) sau khi đã Deploy. Rollback khẩn cấp: Re-deploy lại image/artifact bản cũ ổn định hoặc chuyển luồng traffic (Blue/Green Deployment).
4. Sự cố Hạ tầng
(Runner down, timeout)		 Các lỗi không do mã nguồn (mất kết nối, hết hạn credential API thứ 3). Cơ chế Auto-Retry (có giới hạn số lần). Báo động cho đội vận hành (Ops).

Kiểm Thử Chuyên Sâu

Test Harness (Theo ISO/IEC/IEEE 24765)

"Tập hợp các công cụ, thư viện, dữ liệu kiểm thử và cấu hình được xây dựng để tự động hóa việc chuẩn bị, điều khiển, quan sát và dọn dẹp quá trình thực thi kiểm thử một cách nhất quán."

4 Trách Nhiệm Cốt Lõi Trong Đề Tài:

1. Thiết lập

Cố định Node.js 14.21.3, cài dependency (không có lockfile), khởi tạo network Docker tạm.

2. Điều khiển

Khởi động SUT RealWorld, chờ API `/api/tags` phản hồi HTTP 200, kích hoạt Cypress runner.

3. Quan sát

Ghi exit code, thu thập log container, chụp ảnh/quay video màn hình từ Cypress headless.

4. Dọn dẹp

Xuất báo cáo JUnit/Allure, dọn tài nguyên Docker chính xác theo build label (Zero Leak).

Phân Biệt Các Thuật Ngữ Kiểm Thử Chuyên Sâu

Tránh nhầm lẫn giữa công cụ viết mã kiểm thử và hệ thống thực thi bao quanh nó.

Khái Niệm Chức Năng & Định Nghĩa Ví Dụ Trong Đề Tài
Test Case & Test Suite Tập hợp các điều kiện, hành động và kết quả mong đợi để xác minh một chức năng cụ thể. Nhóm các test case liên quan tạo thành Test Suite. File tests/api/api.test.js chứa các ca kiểm thử đăng nhập, bài viết.
Test Framework/Runner Thư viện cung cấp API (để viết assertion, mock) và cơ chế khám phá, thực thi các Test Suite. Jest, Mocha, Cypress - Cung cấp các hàm describe(), it(), expect().
Test Harness Toàn bộ môi trường và cơ sở hạ tầng giúp test runner hoạt động: khởi động SUT, chuẩn bị dữ liệu, điều khiển runner, thu kết quả và dọn dẹp. Script jenkins/image_smoke.py, mạng Docker tạm, công cụ xuất Allure HTML.
CI/CD Pipeline Quy trình tự động hóa cấp cao hơn, điều phối toàn bộ vòng đời: từ biên dịch (build), qua Harness (test) đến bàn giao (artifact). GitHub Actions (Workflow YAML) và Jenkinsfile.

Phân Tích Lý Thuyết

Các Tính Chất Cốt Lõi Của Một Test Harness Kiến Trúc Tốt

1. Khả Năng Tái Lập (Reproducibility) & Tính Cô Lập (Isolation)

Một ca kiểm thử tự động chỉ có giá trị khi nó trả về kết quả giống nhau ở mọi lần chạy trên cùng một bộ mã nguồn. Harness phải cung cấp môi trường cô lập (như Docker Network riêng), không bị nhiễu bởi các tiến trình khác trên Host để loại trừ hiện tượng Flaky Tests (kiểm thử lúc đúng lúc sai).

2. Khả Năng Truy Vết (Traceability)

Mọi sản phẩm đầu ra (Test Report, Log, Screenshot, Video, Docker Image) phải được liên kết chặt chẽ với nguyên nhân sinh ra nó. Đề tài dùng Full 40-character Git SHA làm khóa truy vết duy nhất, cho phép đối chiếu source revision, image, Jenkins build và report.

3. Tôn Trọng Oracle Kiểm Thử

Harness cung cấp công cụ thu thập chứng cứ, nhưng không thay thế việc lựa chọn đúng Test Oracle (cơ chế quyết định Pass/Fail). Đề tài kết hợp nhiều Oracle: HTTP Status (API), DOM State/URL (Cypress), và Exit Code (Hệ điều hành) để Quality Gate ra quyết định chính xác.

Chiến Lược Kiểm Thử

Xu Hướng Mở Rộng: Shift-Left & Shift-Right

Shift-Left Testing

Đẩy các bài kiểm thử về giai đoạn sớm nhất có thể trong vòng đời phát triển, ngay trên máy của Developer để tiết kiệm chi phí sửa lỗi.

  • Git Hooks (husky): Tự động chạy Lint/Unit Test chặn các commit rác ngay lập tức.
  • PR Pipelines: Pipeline rút gọn chạy siêu tốc (< 10 phút) để feedback tự động qua comment GitHub.
Shift-Right Testing

Thực hiện kiểm thử và giám sát trực tiếp trên môi trường Production, tận dụng dữ liệu và hành vi thật của người dùng.

  • Canary Deployment: Cập nhật bản mới cho nhóm nhỏ user (5%), nếu ổn định mới mở rộng.
  • Synthetic Monitoring: Triển khai Bot mô phỏng kịch bản luồng user để đo tính khả dụng 24/7.

Chiến lược xử lý "Flaky Tests" (Kiểm thử thiếu ổn định)

Test lúc đúng lúc sai gây nghẽn Pipeline. Cách khắc phục: (1) Cấu hình Auto-retry 2-3 lần cho E2E; (2) Cách ly (Quarantine) test hỏng để sửa sau; (3) Xóa bỏ sleep(giây) cứng, thay bằng chờ chủ động (Wait/Polling HTTP Status).

Phân Hệ Đám Mây

GitHub Actions Pipeline: 11 Jobs & SAST

Workflow Chuẩn (ci.yml)

name: CI Pipeline on: [push, pull_request, workflow_dispatch] jobs: unit-test: needs: install steps: [ run: npm run test:unit ] api-test: needs: install steps: [ run: npm run test:api ] security-scan: needs: install steps: [ run: npm audit --audit-level=high ] docker-build: needs: [lint, unit-test, api-test, security-scan] steps: [ run: docker build -t $IMAGE:${{ github.sha }} ]

Hạ Tầng Tự Chủ

Jenkins Harness: Custom Image & Hai Chế Độ

Source Mode (RUN_MODE=source)

  • Baseline kiểm tra trực tiếp mã nguồn.
  • Checkout theo SUT_REF. Install dependency thô.
  • Thực thi Lint, Mocha Tests và Build Next.js nội bộ Jenkins.

Image Mode (RUN_MODE=image)

  • Authenticate & Pull Image bằng Credential ghcr-credentials bảo mật.
  • Tạo container trong mạng riêng ảo, độc lập port host.
  • Chạy script image_smoke.py kiểm tra readiness.
  • Chạy Cypress UI bằng trình duyệt Headless tích hợp.

Jenkins Custom Node & Zero Resource Leak

Jenkins chạy trên Docker compose với Custom Image nhúng sẵn Node 14, Docker CLI, Python 3, Cypress 9.7 và Allure.
Sau mỗi Build, block post.always đảm bảo dọn sạch các mạng con và container SUT có nhãn sở hữu tương ứng, không dùng prune toàn cục gây lỗi chéo.

Kết Luận & Định Hướng

Đánh Đổi Thiết Kế, Khó Khăn & Hướng Phát Triển

Đánh Đổi & Thành Công

  • Thành công Truy Vết: Single Source of Truth thông qua Git SHA cho Image thay vì dùng latest.
  • Đánh Đổi Image Jenkins: Image khá lớn do cài Cypress (Electron/Browsers), nhưng đổi lại không bị dependency hell khi build node riêng.
  • Bảo Mật Docker: Việc map Docker socket /var/run/docker.sock tiện lợi cho Seminar, nhưng cần kiến trúc Jenkins Agent bảo vệ trên Production thật.

Khó Khăn & Kế Hoạch Tương Lai

  • Vấn đề Legacy: Ứng dụng dính chặt với Node 14 và không có package-lock.json khiến bản dựng thiếu tất định. Sắp tới cần cố định Lockfile.
  • Mở rộng Coverage: Mục tiêu tiến tới quét toàn bộ các file Model/Route thay vì giới hạn ở cục bộ.
  • Mở rộng luồng UI: Bổ sung E2E test cho luồng Authentication (đăng nhập thành công, thao tác bài viết, đăng xuất).
