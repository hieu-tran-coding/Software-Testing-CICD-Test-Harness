Nền Tảng Tự Động Hóa

Ba Mức Độ Tự Động Hóa Trong Phát Triển

Continuous Integration (CI)

  • Tích hợp thay đổi vào nhánh dùng chung thường xuyên.
  • Tự động Build và Test (Lint, Unit, API) ngay lập tức.
  • Phát hiện sớm lỗi biên dịch và xung đột.
  • Nhóm áp dụng: GitHub Actions chặn mã nguồn lỗi gộp bằng Quality Gates.

Continuous Delivery (CD)

  • Duy trì phần mềm ở trạng thái luôn sẵn sàng phát hành.
  • Tự động đóng gói Artifact (Docker Image).
  • Cần phê duyệt thủ công mới lên production.
  • Nhóm áp dụng: GHCR lưu trữ image gắn Git SHA, bàn giao cho Jenkins.

Continuous Deployment

  • Tự động hóa hoàn toàn đến tận môi trường Production.
  • Không cần phê duyệt thủ công.
  • Yêu cầu bộ test cực kỳ đáng tin cậy.
  • Pipeline của hệ thống chỉ tập trung ở mức CI và Continuous Delivery.

Phân Tích Lý Thuyết CI/CD

Pipeline, Quality Gates & Nguyên Tắc Fail-Fast

Khái niệm Pipeline

Pipeline là sự mô hình hóa quy trình phân phối phần mềm thành các bước có thứ tự hoặc quan hệ phụ thuộc lẫn nhau. Nó chuyển đổi mã nguồn thô thành một sản phẩm có thể triển khai: Chuẩn bị → Kiểm tra → Đóng gói.

Quality Gate (Cổng Chất Lượng)

Là điều kiện bắt buộc phải đạt trước khi artifact được chuyển sang giai đoạn sau. Nếu Unit Test hoặc Security Scan thất bại, Quality Gate sẽ đóng lại, ngăn chặn mã nguồn lỗi bị merge hoặc deploy.

Nguyên tắc Fail-Fast trong thiết kế

Cho phép dừng sớm toàn bộ Pipeline ngay khi một bước bắt buộc thất bại (ví dụ: lỗi cú pháp Lint). Giúp tiết kiệm tài nguyên máy chủ CI, đưa ra phản hồi tức thì cho Developer sửa lỗi thay vì phải đợi hàng chục phút.

Phân Tích Lý Thuyết CI/CD

Tính Kháng Lỗi (Resilience): Kịch Bản Xử Lý Sự Cố

Pipeline không chỉ phục vụ luồng chạy thành công (Happy Path) mà quan trọng hơn là cơ chế xử lý khi xảy ra sự cố.

Trường Hợp Sự Cố Phát Hiện & Tác Động Chiến Lược Xử Lý Đề Xuất
1. Lỗi Code ở pha CI
(Compile error, Test fail)		 Phát hiện sớm ở bước 1–6. Pipeline bị chặn ngay lập tức (Fail-Fast). Ngăn chặn lệnh Merge. Gửi cảnh báo tức thì. Developer sửa mã nguồn trên nhánh phụ và push lại.
2. Lỗi sau khi Merge
(Lọt qua CI)		 Phát hiện ở Staging hoặc do review muộn sau khi mã đã vào nhánh main. Sử dụng lệnh git revert để tạo commit đảo ngược an toàn. Tuyệt đối không dùng git reset.
3. Sự cố trên Production
(Lỗi runtime, hiệu năng)		 Phát hiện qua hệ thống Monitoring (bước 11) sau khi đã Deploy. Rollback khẩn cấp: Re-deploy lại image/artifact bản cũ ổn định hoặc chuyển luồng traffic (Blue/Green).
4. Sự cố Hạ tầng
(Runner down, timeout)		 Các lỗi không do mã nguồn (mất kết nối, hết hạn credential API thứ 3). Cơ chế Auto-Retry (có giới hạn số lần). Kích hoạt cảnh báo hệ thống cho đội vận hành (Ops).

Kiểm Thử Chuyên Sâu

Test Harness (Theo ISO/IEC/IEEE 24765)

"Tập hợp các công cụ, thư viện, dữ liệu kiểm thử và cấu hình được xây dựng để tự động hóa việc chuẩn bị, điều khiển, quan sát và dọn dẹp quá trình thực thi kiểm thử một cách nhất quán."

Từ lý thuyết đó nhóm đã áp dụng :

1. Thiết lập

Cố định Node.js 14.21.3, cài dependency (không có lockfile), khởi tạo network Docker tạm.

2. Điều khiển

Khởi động SUT RealWorld, chờ API `/api/tags` phản hồi HTTP 200, kích hoạt Cypress runner.

3. Quan sát

Ghi exit code, thu thập log container, chụp ảnh/quay video màn hình từ Cypress headless.

4. Dọn dẹp

Xuất báo cáo JUnit/Allure, dọn tài nguyên Docker chính xác theo build label (Zero Leak).

Phân Biệt Các Thuật Ngữ Kiểm Thử Chuyên Sâu

Tránh nhầm lẫn giữa công cụ viết mã kiểm thử và hệ thống thực thi bao quanh nó.

Khái Niệm Chức Năng & Định Nghĩa Hiện Thực Trong Pipeline
Test Case & Test Suite Tập hợp các điều kiện, hành động và kết quả mong đợi để xác minh một chức năng cụ thể. Nhóm các test case liên quan tạo thành Test Suite. File tests/api/api.test.js chứa các ca kiểm thử đăng nhập, bài viết.

Test Harness Toàn bộ môi trường và cơ sở hạ tầng giúp test runner hoạt động: khởi động SUT, chuẩn bị dữ liệu, điều khiển runner, thu kết quả và dọn dẹp. Script jenkins/image_smoke.py, mạng Docker tạm, công cụ xuất Allure HTML.
CI/CD Pipeline Quy trình tự động hóa cấp cao hơn, điều phối toàn bộ vòng đời: từ biên dịch (build), qua Harness (test) đến bàn giao (artifact). GitHub Actions (Workflow YAML) và Jenkinsfile.

Phân Tích Lý Thuyết

Các Tính Chất Cốt Lõi Của Một Test Harness Kiến Trúc Tốt

1. Khả Năng Tái Lập (Reproducibility) & Tính Cô Lập (Isolation)

Cung cấp môi trường cô lập (mạng Docker riêng), đảm bảo cùng một mã nguồn luôn cho kết quả kiểm thử nhất quán và loại bỏ triệt để hiện tượng Flaky Tests.

2. Khả Năng Truy Vết (Traceability)

Sử dụng Full 40-character Git SHA làm khóa định danh duy nhất xuyên suốt, liên kết chặt chẽ mọi artifact (Report, Log, Image) với đúng Commit tương ứng.

3. Tôn Trọng Oracle Kiểm Thử

Harness chỉ thu thập chứng cứ, không thay thế cơ chế phán quyết Pass/Fail. Pipeline kết hợp đa tầng Oracle: HTTP Status (API), DOM State (Cypress), và Exit Code hệ điều hành.

Full 40-character Git SHA là gì?

Chuỗi băm SHA-1 duy nhất (40 ký tự) định danh phiên bản commit tuyệt đối trong Git, chống xung đột phiên bản khi bàn giao sang Docker & Harness.

Test Oracle (Cơ chế phán quyết) là gì?

Nguồn tri thức / cơ chế dùng để so sánh hành vi thực tế với kết quả kỳ vọng chuẩn để xác định ca kiểm thử là Pass hay Fail.

Chiến Lược Kiểm Thử

Xu Hướng Mở Rộng: Shift-Left & Shift-Right

Shift-Left Testing

Đẩy các bài kiểm thử về giai đoạn sớm nhất có thể trong vòng đời phát triển, ngay trên máy của Developer để tiết kiệm chi phí sửa lỗi.

  • Git Hooks (husky): Tự động chạy Lint/Unit Test chặn các commit rác ngay lập tức.
  • PR Pipelines: Pipeline rút gọn chạy siêu tốc (< 10 phút) để feedback tự động qua comment GitHub.
Shift-Right Testing

Thực hiện kiểm thử và giám sát trực tiếp trên môi trường Production, tận dụng dữ liệu và hành vi thật của người dùng.

  • Canary Deployment: Cập nhật bản mới cho nhóm nhỏ user (5%), nếu ổn định mới mở rộng.
  • Synthetic Monitoring: Triển khai Bot mô phỏng kịch bản luồng user để đo tính khả dụng 24/7.

Chiến lược xử lý "Flaky Tests" (Kiểm thử thiếu ổn định gây nghẽn Pipeline):

• (1) Auto-retry: Cấu hình chạy lại 2–3 lần cho các bài test E2E để loại trừ lỗi mạng/độ trễ tạm thời.
• (2) Cách ly (Quarantine): Tách các test hỏng ra khỏi luồng CI chính để sửa sau, tránh chặn PR.
• (3) Chờ chủ động: Xóa bỏ hoàn toàn sleep(giây) cứng, thay bằng thăm dò HTTP Status / DOM State.

Hạ Tầng Tự Chủ

Chi Tiết Hai Chế Độ & Cơ Chế Zero Resource Leak

Source Mode (RUN_MODE=source)

  • Môi trường đối chứng (Baseline Check) trực tiếp trên source Git.
  • Checkout theo SUT_REF, cài đặt dependency thô trên agent.
  • Thực thi Lint, Mocha Tests và biên dịch Next.js trong workspace.
  • Giúp xác nhận mã nguồn có thể lint/test độc lập ngoài Docker.

Image Mode (RUN_MODE=image)

  • Kéo Docker Image từ GHCR qua Secret ghcr-credentials an toàn.
  • Tạo container trong mạng riêng ảo nội bộ, không cần mở port ra host.
  • Script image_smoke.py thăm dò readiness qua /api/tags.
  • Thực thi 5 ca Cypress Headless UI và xuất bản Allure Report HTML.

Cơ Chế Custom Agent & Dọn Dẹp Zero Resource Leak

Custom Jenkins Image nhúng sẵn Node 14, Docker CLI, Python 3, Cypress 9.7 và Allure. Khối post.always đảm bảo dọn dẹp chính xác container và mạng theo nhãn sở hữu của phiên build (kể cả khi test thất bại), tuyệt đối không dùng prune gây xung đột các job song song.

Hướng Dẫn Thiết Lập Workflow CI/CD • Tệp Cấu Hình 1

Cấu Trúc Tổng Quát Tệp YAML Pipeline Chính (CI Workflow)

ci-pipeline-template.yml Template 
name: <Tên_Pipeline_Hiển_Thị>

on:  # Các sự kiện kích hoạt (Triggers)
  push:
    branches: [ "main", "next" ]
  pull_request:
    branches: [ "main" ]
  workflow_dispatch:  # Kích hoạt thủ công

permissions:
  contents: read  # Quyền hạn tối thiểu (Least Privilege)

env:  # Khai báo các biến môi trường dùng chung
  RUNTIME_VERSION: '14.21.3'
  IMAGE_REGISTRY: ghcr.io/${{ github.repository }}

jobs:
  lint-check:  # 1. Kiểm tra định dạng & cú pháp
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci && npm run lint

  automated-test:  # 2. Chạy Test Suite & Cổng Chất Lượng
    needs: lint-check  # Fail-Fast: Chặn sớm nếu lint lỗi
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm run test:coverage  # Ngưỡng Quality Gate >= 80%
      - uses: actions/upload-artifact@v4
        if: always()  # Thu thập report kể cả khi test fail
        with: { name: test-report, path: test-reports/ }

  build-artifact:  # 3. Đóng gói Container Image
    needs: [ lint-check, automated-test ]  # Quality Gate
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: docker build -t $IMAGE_REGISTRY:${{ github.sha }} .

Lưu Ý Cốt Lõi Khi Viết YAML Pipeline

  • 1. Thụt lề (Indentation): Dùng đúng 2 khoảng trắng; không được dùng phím Tab (gây lỗi parse cú pháp).
  • 2. Phân cấp thực thi: Workflow → Jobs (chạy song song) → Steps (chạy tuần tự).
  • 3. Cơ chế Fail-Fast: Dùng needs: chặn ngay các job sau nếu Lint/Test lỗi để tiết kiệm runner.
  • 4. Thực thi lệnh: Dùng uses: gọi Action có sẵn; dùng run: thực thi lệnh shell nội bộ.
  • 5. Bằng chứng lỗi: Luôn đặt if: always() khi upload artifact để không bỏ sót báo cáo khi test fail.

Cấu Trúc Tổng Quát Tệp YAML Quét An Ninh (Security SAST)

security-sast-template.yml DevSecOps 
name: <Tên_Quy_Trình_Bảo_Mật_SAST>

on:
  push:
    branches: [ "main", "next" ]
  pull_request:
    branches: [ "main" ]
  schedule:
    - cron: '<phút> <giờ> <ngày> <tháng> <thứ>'  # Quét tự động định kỳ
  workflow_dispatch:

jobs:
  security-analysis:
    runs-on: ubuntu-latest
    permissions:
      actions: read
      contents: read
      security-events: write  # Bắt buộc để tải báo cáo SARIF

    strategy:
      fail-fast: false  # Cho phép các ngôn ngữ khác tiếp tục quét
      matrix:
        language: [ '<ngôn_ngữ_1>', '<ngôn_ngữ_2>' ]

    steps:
      - name: Checkout source code
        uses: actions/checkout@v4

      - name: Initialize Security Engine
        uses: github/codeql-action/init@v3
        with:
          languages: ${{ matrix.language }}
          queries: <bộ_quy_tắc_bảo_mật_mở_rộng>

      - name: Execute Analysis & Upload Results
        uses: github/codeql-action/analyze@v3
        with:
          category: "/language:${{ matrix.language }}"

Hiểu Nhanh Về Quét An Ninh (SAST) & Lưu Ý Cấu Hình

  • 1. SAST là gì? Là công cụ tự động "soát lỗi an ninh" trên mã nguồn (tìm nguy cơ lộ mật khẩu, chèn mã độc...) mà không cần phải chạy server.
  • 2. Tách biệt Pipeline: Vì việc rà soát code tốn nhiều thời gian hơn, nên tách riêng tệp YAML để không làm chậm chu trình build/test thường ngày.
  • 3. Quét định kỳ (schedule.cron): Thư viện bên thứ ba có thể phát sinh lỗ hổng mới bất kỳ lúc nào; hẹn giờ quét tự động giúp phát hiện sớm dù không có commit mới.
  • 4. Quyền hiển thị cảnh báo: Bắt buộc cấp security-events: write để CodeQL gắn thẻ cảnh báo trực tiếp trên giao diện GitHub, chỉ rõ dòng code cần sửa.
  • 5. Mức độ soi lỗi (queries): Thiết lập độ khắt khe của bộ lọc an ninh (như security-extended), từ kiểm tra chất lượng code cơ bản đến các lỗi nguy hiểm (SQLi, XSS).
